# Twilight 双重验证（2FA）设计草案

日期：2026-09-30  
作者：Carinoasd  
状态：用户已确认，按推荐方案实施。

## 目标与推荐方案

完成需求第 5 项：后台提供 2FA 设置开关，用户可在账户设置中启用和关闭自己的 2FA。管理员账户使用同一套个人设置。密码登录和 Telegram 扫码登录都接入第二步验证。

| 方案 | 使用方式 | 取舍 |
| --- | --- | --- |
| 验证器 App + 一次性备用码（推荐） | 扫描设置二维码，登录时输入验证码；手机遗失时使用备用码 | 不依赖邮件或 Bot 投递，需要保管备用码 |
| 邮箱验证码 | 登录时接收邮件验证码 | 用户容易理解，但依赖邮件投递和邮箱账户安全 |
| Passkey | 使用设备解锁验证 | 更适合后续独立功能，需要另行设计跨设备注册和恢复 |

本轮采用第一种。后台不强制所有用户或管理员注册 2FA；强制策略如有需要另行确定。

## 一、后台开关与个人开关

- 后台安全设置新增「允许用户启用双重验证」，默认关闭。管理员和普通用户的个人启用流程一致。
- 开关只控制新启用及设置请求。关闭时撤销尚未完成的设置请求，已启用账户仍须通过第二步验证，也仍可使用备用码和安全地关闭个人 2FA。
- 已启用账户的第二步验证不能因为后台开关关闭而被跳过。界面直接说明这一点。
- 后台只显示是否准备好加密密钥，不显示密钥内容。未准备好时解释原因并拒绝启用。
- 个人设置显示启用状态、启用时间和剩余备用码数量。

## 二、用户启用、关闭与恢复

1. 用户登录后输入当前 Twilight 密码，创建有效期 10 分钟的设置请求。同一用户最多保留一份，新的请求替换旧请求。
2. 页面本地生成验证器二维码，同时提供可手动输入的设置密钥。二维码和密钥只出现在本次设置页面，不经过第三方图片服务。
3. 用户输入验证器中的有效验证码后，服务端原子启用 2FA，生成 10 个高熵、一次性备用码。
4. 备用码只在这次成功响应中展示，用户可主动复制或下载；页面提醒保存并提供完成按钮。刷新后不再显示原文。响应丢失时，用户可重新登录后重新生成。
5. 启用成功即吊销旧会话及未完成的登录请求。页面保留本次备用码展示，完成后重新登录。
6. 关闭 2FA 或重新生成备用码，必须验证当前密码，以及有效验证码或一枚未使用的备用码。重新生成会使全部旧备用码失效。
7. 使用备用码登录不会自动关闭 2FA。普通密码找回、Emby 密码验证和管理员重设密码也不会清除 2FA。
8. 手机和备用码同时遗失时，提供服务器控制台的单用户紧急重置命令：指定 UID、明确确认、记录审计并吊销相关会话。管理员应先在线下核实本人身份；本轮不增加可远程免验证清除他人 2FA 的按钮。

## 三、登录流程

- 未启用 2FA：保留现有登录结果。
- 已启用 2FA：密码验证成功或 TG Bot 确认并兑换扫码请求后，只签发有效期 3 分钟的第二步验证请求；此时不发送正式会话 Cookie，不返回可用登录 Token，也不触发登录成功通知。
- 用户输入验证码或备用码后，服务端验证并一次性消费请求，再建立正式会话、记录登录和发送已有登录通知。
- 请求绑定 UID、浏览器设备标识、第一步验证方式及账户安全版本；Token 使用随机值，数据库只存摘要。页面只在内存保存，刷新或取消须重新开始登录。
- 每个请求最多 5 次错误尝试，账户及 IP 另有限流；有效验证码和备用码的消费必须跨进程原子执行，并发兑换只能成功一次。
- TOTP 使用标准 30 秒时间步长、6 位数字，允许相邻一个时间步的时钟偏差。已成功消费的时间步不得再次使用。
- 账户禁用、删除、密码或身份变更、设备封禁、2FA 状态变化、登出全部、恢复数据时，旧验证请求失效。安全字段改回旧值也不能使旧请求复活。
- TG 发起的第二步请求仍受 TG 登录开关及当时绑定身份约束。第二步完成前关闭 TG 登录或换绑，必须重新开始。
- 会话创建失败后不复活已经消费的凭据；提示重新开始登录。恢复接口错误时不自动重复提交备用码。

## 四、数据与密钥

- 新增专用 PostgreSQL 表保存已启用的验证器密文、备用码摘要、安全版本和已消费时间步；临时设置及登录请求单独保存并定期清理。
- 验证器密钥使用 AES-256-GCM 加密，以 UID 和格式版本绑定密文。备用码使用随机生成的高熵值，只保存带用途区分的摘要。
- 实例加密主密钥通过部署环境变量提供，使用独立的 32 字节随机密钥；不复用 Bot Token、数据库密码或现有内部密钥，不允许通过网页读取或修改。
- 所有 API 副本须使用相同主密钥。部署说明包含生成、保存、启动配置和恢复方式；启用 2FA 前必须完成配置。
- 主密钥缺失或错误时，已启用账户的验证应明确失败，不能退化为单因素登录；数据库中其余功能的数据不得因此被重写或清空。
- 业务备份和迁移必须包含已启用的 2FA 密文与备用码摘要，不包含临时请求或主密钥。恢复到另一台服务器前必须配置匹配密钥；验证失败时，在覆盖数据库前拒绝恢复。
- 导入包含 2FA 的数据后，清空临时请求并吊销旧会话。没有 2FA 字段的旧备份保留显式整体恢复语义，预览提示其会覆盖目标账户的 2FA 状态；需要现有恢复确认，不能把缺字段当作普通更新。
- 2FA 变更与登录签发采用一致的锁顺序和安全版本检查；Redis 或内存中的旧会话不能绕过 PostgreSQL 的新安全状态。
- 密钥、验证码、备用码原文和临时凭据不得出现在通用账户响应、公开能力、审计、错误日志或前端持久化状态中。设置二维码、一次性备用码展示及登录请求签发的专用响应，只向完成相应前置验证的调用方返回必要凭据，并设置禁止缓存。

## 五、代码落点与界面

- `internal/security`：验证码、密钥加解密及备用码工具，使用标准算法并验证公开测试向量。
- `internal/store`：版本化表结构、原子消费、生命周期清理、备份恢复和跨进程失效。
- `internal/api`：共享第二步验证服务，接入 `login_service.go` 和 `telegram_login.go`；V1 登录适配器共用验证规则，新增功能资源使用 V2。
- 检查会话续期、改密后重新签发、首次初始化管理员等所有创建会话的位置，禁止未完成 2FA 的请求进入这些路径。
- 后台复用配置 schema 和现有安全页面；个人设置新增独立 2FA 组件，避免继续扩大设置页面内联逻辑。
- 登录页共用第二步验证码界面，支持切换备用码、剩余时间、取消和过期后重新登录；密码登录和 TG 登录使用相同的结果类型。
- 保持原来的安全跳转目标；简体、繁体、英文同时完成，Firefox 手机、平板和桌面布局均验证。
- CORS／CSRF 实现不修改，不修改正式站配置，不自动部署。

## 六、验收与交付

1. 算法测试：标准向量、时间边界、重放、密文篡改、错误密钥及备用码单次消费。
2. 数据库测试：两个 Store 实例并发、重启持久化、安全状态修改后恢复旧值、过期、次数限制、恢复和迁移。
3. API 测试：密码/TG 两条路径都必须完成第二步；未完成前无会话；V1、会话续期、密码重设和设备封禁不可绕过；关闭后台开关不影响已有保护。
4. 前端测试：启用、关闭、备用码重新生成、密码及 TG 登录、错误和过期处理；取消后的迟到响应不能更新状态；敏感值不进入浏览器持久化存储。
5. 运行完整后端测试、前端类型检查、代码检查、测试、构建及文档一致性检查，Firefox 验证三个语言和三个屏幕尺寸。
6. 独立分支提交并开 PR。依赖 #116 的扫码登录服务；开 PR 前确认其最新状态并选择正确基线，不将本轮改动混入 #116。

## 依据

- [RFC 6238：TOTP](https://www.rfc-editor.org/info/rfc6238/)：时间步长、时钟偏差、密钥保护及禁止重复接受成功验证码。
- [OWASP：多因素认证](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)：恢复途径、备用码及变更认证因素时重新验证身份。

已检查：开关含义与登录规则一致；密钥部署、恢复、丢失手机、扫码入口与旧会话均有处理方案；本轮没有强制注册策略或其他独立功能。
